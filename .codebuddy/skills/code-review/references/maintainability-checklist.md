# 维度 4：可维护性检查清单

评估代码可读性、复用性、测试覆盖及文档完整性。

## 4.1 可读性

- [ ] 命名准确表达意图（避免 `data2`、`handleIt`、单字母命名作用于大范围）；
- [ ] 函数/组件长度与嵌套深度：超长函数（如 >50 行）、超过 3 层的嵌套（应 early return / 提取函数）；
- [ ] 复杂表达式无解释，魔法数字无命名常量；
- [ ] 死代码：注释掉的大段代码、不可达分支、未使用的导入与变量；
- [ ] 注释质量：注释解释"为什么"而非复述"做什么"；过时注释误导读者的优先报告。

## 4.2 复用性

- [ ] 复制粘贴的重复逻辑（>=2 处相同或近似代码块应提取）；
- [ ] 已有共享工具/组件被绕过，重新造轮子（对照项目共享目录既有导出）；
- [ ] 配置/常量散落多处定义（单一事实来源被破坏）；
- [ ] 类似逻辑因微小差异各自维护，可参数化合并。

## 4.3 类型与契约

- [ ] 关键公共接口（API schema、组件 props、服务函数签名）有明确类型定义；
- [ ] 大量 `any`/`as any`/类型断言绕过检查集中在数据边界；
- [ ] 导出的类型/函数与实际行为一致（命名与返回值语义不误导）。

## 4.4 错误处理

- [ ] 外部调用（网络、数据库、文件）有无失败路径处理；
- [ ] 空 `catch`/吞异常（捕获后既不处理也不上报不记录）；
- [ ] 错误信息可定位（包含足够上下文，而非裸 `throw new Error('failed')`）；
- [ ] 用户可见错误与内部错误的区分（不向用户暴露内部细节）。

## 4.5 测试覆盖

- [ ] 核心业务逻辑有无对应测试（对照项目测试目录约定）；
- [ ] 修改既有行为是否同步更新了测试；
- [ ] 边界条件（空输入、极大输入、并发、失败重试）是否被覆盖；
- [ ] 测试本身质量：是否断言了行为而非实现细节、是否存在永真断言。

## 4.6 文档完整性

- [ ] 公共模块/API 有无最小使用说明（导出函数 docstring/JSDoc）；
- [ ] 新增架构性决策是否留下记录（对照项目是否有 ADR/规格文档约定，如 `docs/spec/adr/`）；
- [ ] 破坏性变更（接口签名、数据格式、配置项）是否更新了 README/CHANGELOG/调用方；
- [ ] 运行手册类内容（启动参数、环境变量）是否同步。

## 判定原则

- 可读性问题仅在确实增加理解成本时报，纯风格问题交给 lint 工具与项目格式化配置，不重复报告；
- 测试缺失按"核心逻辑无测试"为 P1、"外围功能无测试"为 P2 掌握；
- 文档要求以项目自身规范为基准（如项目规定"新模块必须写 onboarding 文档"，则缺失即为问题）。
