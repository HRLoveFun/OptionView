# 维度 3：效率检查清单

关注性能瓶颈、资源利用率、算法复杂度及可扩展性。

## 3.1 算法与数据结构

- [ ] 嵌套循环中的隐式 O(n²)（循环内执行 `includes`/`find`/`filter` —— 应改用 `Set`/`Map` 索引）；
- [ ] 循环内重复计算可提取的不变量；
- [ ] N+1 查询：循环内逐条发起数据库/HTTP 请求，应改批量或预加载；
- [ ] 不必要的深拷贝/全量复制（大对象、大数组）；
- [ ] 递归无剪枝或无记忆化，可能随规模指数增长。

## 3.2 数据库与数据访问

- [ ] 查询是否命中索引（`WHERE`/`JOIN`/`ORDER BY` 字段）；
- [ ] `SELECT *` 拉取全表后在应用层过滤/聚合；
- [ ] 大结果集无分页/无 `LIMIT`；
- [ ] 事务范围过大：把非必要的慢操作（HTTP 调用、文件 IO）包进事务，长时间持锁；
- [ ] 高频路径中是否重复查询可缓存的静态数据（对照项目是否已有预计算表/缓存约定——若项目规范要求读预计算表而代码在实时聚合，属违规）。

## 3.3 前端专项

- [ ] 列表渲染缺 `key` 或以 index 作 key 导致大面积重渲染；
- [ ] 大列表无虚拟化（数千条目直接渲染）；
- [ ] 重计算未 memo 化，且每帧/每次 render 重算；
- [ ] 打包体积：引入了整库（`import * as _`）、未按需加载的重型依赖；首屏未拆包；
- [ ] 状态设计导致全局重渲染：高频数据流（如实时行情/订单流）写入引发大范围订阅更新的 Context，应下沉到局部 store（如 Zustand）或做 selector 细粒度订阅；
- [ ] 未防抖/节流的 `resize`/`scroll`/输入事件处理。

## 3.4 后端与并发

- [ ] 阻塞调用占据事件循环/线程池（同步 IO 混入异步框架、CPU 密集任务占用请求线程）；
- [ ] 连接/资源未复用：每请求新建数据库连接、HTTP client；
- [ ] 未设超时的外部调用（可挂死线程）；
- [ ] 无界队列/缓存（无淘汰策略，内存持续增长）；
- [ ] 锁粒度过大或存在明显竞态窗口。

## 3.5 资源与可扩展性

- [ ] 文件句柄、流、订阅是否在使用后关闭/取消（Python `with`、前端 abort/取消订阅）；
- [ ] 一次性加载全量数据到内存的模式（应流式处理）；
- [ ] 水平扩展障碍：依赖本地内存保存跨请求状态、本地文件作为持久存储；
- [ ] 日志量：高频循环内打日志导致 IO 瓶颈。

## 判定原则

- 以实际数据规模推断影响：在 10 行数据上的 O(n²) 不构成问题，在 10 万行上则是 P1；
- 不做投机优化建议：没有证据表明会成为瓶颈的热路径微优化记为 P3 或不报；
- 涉及"架构级"性能（如项目规范强制走预计算表）的违规优先级提升一级。
