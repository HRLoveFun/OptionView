# 代码评审报告模板

输出报告时遵循以下结构。标题级别与措辞可按评审规模微调，但五大部分顺序不变。

```markdown
# 代码评审报告：<评审对象标题>

**评审模式**：全库 / 变更集（base..head）/ 定点
**评审范围**：<全库：模块清单与文件总数；变更集：base..head 的 SHA 范围或变更文件数；定点：目录/文件>
**需求来源**：<全库：项目整体目标文档；变更集：specs 路径 / issue 编号 / 对话任务描述；未找到写"未提供，架构对齐评价已降级为疑点">
**项目类型**：前端 / 后端 / 全栈 / 基础设施
**评审日期**：<YYYY-MM-DD>

## 一、总体评价

<2-4 句：代码整体质量、是否可合入/可交付、主要风险概述。>

**结论**：<可合入 / 修改后合入 / 需重大修改>

## 二、安全审计结果

<依赖审计命令执行情况与汇总；无依赖清单或命令失败时写明原因。>

- **执行情况**：<如 `npm audit --json` 于项目根目录执行成功 / `pip-audit` 未安装，原因：...>
- **漏洞汇总**：critical <n> / high <n> / moderate <n> / low <n>，无漏洞时写"未发现已知漏洞"
- **高危明细**：<包名、当前版本、CVE 编号、修复版本、是否出现在变更代码调用点；无则写"无">

## 三、问题清单

### P0 阻断问题

#### [安全] <问题标题>
- **位置**：`path/to/file.py` L<start>-<end>（或函数/组件名）
- **现状**：
  ```<lang>
  <最小必要代码片段>
  ```
- **问题**：<现状与风险的具体描述>
- **建议**：<具体、可操作的修复方式；必要时给出修改示例>

<无问题时写：无。>

### P1 严重问题
<同上结构>

### P2 建议项
<同上结构，可精简片段>

### P3 提示项
<同上结构，可精简片段>

## 四、待确认疑点

| # | 位置 | 疑点 | 需要作者确认的内容 |
|---|---|---|---|
| 1 | `path/to/file` L12 | <观察到的现象> | <具体问题> |

<无时写：无。>

## 五、亮点（可选）

- <值得肯定的设计决策或实现，注明位置>

## 六、问题统计

| 维度 | P0 | P1 | P2 | P3 | 合计 |
|---|---|---|---|---|---|
| 架构一致性 | | | | | |
| 安全性 | | | | | |
| 效率 | | | | | |
| 可维护性 | | | | | |
| **合计** | | | | | |
```

## 全库回顾报告差异

全库模式下在标准结构基础上做以下增补/替换：

1. **总体评价 → 库级健康度结论**：四维（架构/安全/效率/可维护性）各给 1-5 分与一句依据，并指出最大风险；结尾给出整改路线。

```markdown
## 〇、模块覆盖与热度

| 模块 | 评审深度 | 问题数（P0/P1/P2/P3） | 健康度简评 |
|---|---|---|---|
| <模块/目录> | 深审 / 抽样 / 仅扫描 | 0/1/3/5 | <一句话> |

**覆盖度声明**：跨切面扫描覆盖 <n> 个文件（100%）；深审模块 <列表>；抽样 <比例与对象>；未深审部分不排除存在问题。

## <编号>、跨模块系统性问题

<每个系统性问题独立成条：模式描述、代表性样例（文件:行号）、全部影响位置清单、统一修复方向。>
<如：5 个模块各自实现了相似的分页逻辑 → 建议收敛到 shared 模块。>

## <编号>、整改路线

| 批次 | 内容 | 预估范围 | 依赖 |
|---|---|---|---|
| 第 1 批 | P0 安全问题 | <文件/模块清单> | 无 |
| 第 2 批 | P1 架构/性能问题 | <...> | 第 1 批 |
| 第 3 批 | P2/P3 可维护性 | <...> | 无硬依赖 |
```

2. **问题清单**仍按 P0-P3 全局排序（系统性问题可在条目中标注"系统性"并引用跨模块章节）。
3. **结论措辞**：全库模式无"可合入"语义，改为"健康度：<良好 / 需要整改 / 存在阻断风险>"。

## 填写要求

1. 每条问题必须包含：问题分类、严重程度、具体位置、现状与期望、改进建议五要素，缺一不可。
2. 代码片段引用最小必要上下文（通常 3-10 行），并标注语言。
3. 改进建议要具体到"怎么改"，避免只说"应该优化""建议重构"。
4. 同一根因的多个表象合并为一条问题，在"问题"字段中列出全部相关位置。
5. 问题标题格式：`[分类] 简明标题`，分类取值：架构 / 安全 / 效率 / 可维护性。
