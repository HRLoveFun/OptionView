# 维度 1：架构设计与任务目标一致性检查清单

评估项目结构、模块划分、依赖关系是否与业务目标和开发任务对齐。

## 1.1 目标对齐

- [ ] 当前实现是否直接服务于明确的业务目标/任务描述？能否从代码结构反推出任务意图？
- [ ] 是否存在与任务无关的"顺手实现"（scope creep）——做了任务没要求的事？
- [ ] 是否遗漏了任务隐含的必要部分（如任务要求"支持导出"，但只做了 UI 未做数据流）？
- [ ] 技术选型是否与项目既有技术栈一致？引入新依赖/新框架是否有充分理由并已在文档中说明？

## 1.2 模块划分与分层

- [ ] 模块边界是否清晰？每个模块是否有单一、可陈述的职责？
- [ ] 是否存在分层破坏：跨层直接引用（如 UI 层直接操作数据库、路由层直接写 SQL）、绕过既有门面/适配器？
- [ ] 公共代码放置位置是否正确（共享代码 vs 模块私有代码，参考项目结构规范）？
- [ ] 循环依赖：模块间是否存在 A→B→A 的引用环？
- [ ] 文件放置是否符合项目规范（对照项目结构文档，如 `docs/spec/project-structure.md` 类似文件）？

## 1.3 依赖关系

- [ ] 依赖方向是否合理：下层（领域/核心逻辑）是否被上层（接口/UI）依赖，而非反向？
- [ ] 对外部服务的依赖是否通过适配器/接口隔离，还是直接深引用其内部实现？
- [ ] 是否存在"隐式耦合"：通过共享全局状态、环境变量、魔法字符串跨模块通信？
- [ ] 第三方依赖是否集中在有限的封装点，便于将来替换？

## 1.4 过度设计（Over-engineering）

出现以下信号时标记为过度设计：

- 为单一实现预留的抽象层/接口（只有一个实现且无可预见的第二实现）；
- 引入重型框架/模式（事件总线、插件系统、微服务拆分）解决简单问题；
- 过深的泛化：大量配置项、泛型参数，但当前只有一种用法；
- 提前优化：为假设中的规模做了当前规模不需要的架构投入。

## 1.5 设计不足（Under-engineering）

出现以下信号时标记为设计不足：

- 领域逻辑散落在多处重复实现，无单一事实来源；
- 关键业务规则硬编码（魔法数字、内嵌 SQL、写死的枚举）而无集中管理；
- 错误处理、边界条件、并发场景完全未考虑；
- 模块已出现明显的职责混杂（一个文件/类承担 5 种以上职责）而无拆分计划；
- 数据所有权不清：多个模块直接读写同一份数据且无所有权约定。

## 1.6 一致性

- [ ] 新代码是否遵循项目既有模式（对照项目内同类模块的写法）？
- [ ] 命名、目录组织是否与项目惯例一致（对照项目编码规范）？
