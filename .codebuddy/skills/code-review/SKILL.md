# 通用代码回顾（Code Review）

对代码库执行四维度系统化评审并输出结构化报告；评审结束后自动复盘并迭代自身规则。

**任务目标：全库回顾**——面向整个代码库的系统性评审，产出库级健康度结论与整改路线。变更集（diff/PR）与定点（指定目录/文件）评审作为轻量分支复用同一套清单与分级标准，但跳过全库编排。

## 评审输入（开始前必须明确）

| 输入要素 | 说明 | 缺省处理 |
|---|---|---|
| 评审模式 | **全库**（默认任务目标）/ 变更集（diff，base..head SHA）/ 定点（指定目录/文件） | 用户说"全库回顾/代码回顾/全库评审/整体检查/整体回顾"→ 全库；说"审查这次改动/PR"→ 变更集；指定了目录或文件 → 定点 |
| 代码库范围 | 模块/目录清单或 diff 范围 | 全库模式：以仓库根为起点盘点全部模块；其余模式：指定内容即为范围 |
| 语言 | 主语言与次语言（如 TypeScript + Python） | 从文件扩展名、依赖清单、CI 配置推断，报告中注明"推断" |
| 框架 | Web 框架、UI 框架、测试框架、ORM 等 | 从依赖清单与配置文件推断，报告中注明"推断"；命中语言专项清单则启用 |
| 变更类型（变更集模式） | 新功能 / 缺陷修复 / 重构 / 依赖升级 / 配置变更 | 从 commit message 与 diff 特征推断 |
| 需求来源 | 全库模式：项目整体目标（README/架构文档/specs）；变更集模式：对应 issue/任务描述 | 未找到时按第一步规则降级为疑点 |

## 工作流总览

七步顺序执行，覆盖五类回顾动作（静态检查、逻辑分析、安全漏洞、性能、可维护性）。**全库模式为主线路径**（步骤 1-7 完整执行）；变更集/定点模式复用步骤 2-7 的清单与分级，仅跳过全库编排：

| 环节 | 内容 | 所在步骤 |
|---|---|---|
| 输入与全库摸底 | 模式确认、模块盘点、优先级分层、需求锚定 | 第一步 |
| 依赖审计 | `npm audit` / `pip-audit` 等命令化漏洞扫描 | 第二步 |
| 静态检查 | lint / 类型检查 / 构建 / 既有测试（工具先行，全库运行） | 第三步 阶段 A |
| 人工分析 | 跨切面全库扫描 + 重点模块深审（逻辑 → 安全 → 性能 → 可维护性 → 架构对齐） | 第三步 阶段 B-F |
| 定级与输出 | P0-P3 分级（三档沟通口径）、结构化报告（全库含覆盖度与整改路线） | 第四、五步 |
| 闭环 | 整改计划、修复验证、复审、回归核对 | 第六步 |
| 自迭代 | 复盘收集 → 改进建议 → 落地 | 第七步 |

## 评审流程

### 第一步：确定评审模式、项目类型与上下文

1. **确定评审模式**：
   - 用户指明"全库回顾"/全库/整体/健康度检查 → 全库模式（主线路径）；
   - 指定了文件/目录/diff/commit → 定点或变更集模式，评审范围即为指定内容；
   - 无法判断 → 默认**全库模式**并在报告注明。
2. **识别项目类型与语言/框架**（输入要素表），决定各维度清单的侧重：
   - **前端**：React/Vue 等框架、构建工具、浏览器运行时；
   - **后端**：API 服务、数据访问层、数据库交互；
   - **全栈**：前后端均评审，重点检查接口契约与数据流；
   - **基础设施**：Dockerfile、CI/CD 配置、IaC（Terraform 等）、部署脚本。
3. 读取项目内的规范文档（如 `AGENTS.md`、`CODEBUDDY.md`、`CLAUDE.md`、`CONTRIBUTING.md`、lint 配置），将其作为项目特有约定的补充评审依据。
4. **收集评审上下文（维度 1 的对照基准，必须执行）**：
   - **全库模式——库级摸底（必须产出，作为后续编排的依据）**：
     - **模块盘点**：遍历仓库结构，产出模块/分层清单（目录、职责推断、规模行数、语言栈）；
     - **热点识别**：用 `git log --format= --name-only` 统计近 90 天（或全部历史）改动频率，识别高 churn 文件/模块；
     - **耦合概览**：用 grep/LSP 索引统计跨模块 import 方向，标记疑似循环依赖与跨层引用；
     - **优先级分层**：按「核心业务模块 > 公共共享层 > 入口/配置 > 外围工具」排序，分层依据 = 改动频率 × 被依赖数（fan-in）× 规模复杂度；产出 Top-N 深审名单（默认 N=3-5，向用户确认）。
   - **变更集模式**：用 `git log`/`git rev-parse` 确定基线（如 `origin/main` 或用户指定的 base commit）与目标 commit，形成明确的 SHA 范围或文件清单，并在报告"评审范围"中写明；范围过大时向用户确认是否拆分评审。
   - **需求来源定位**：
     - 全库模式：以项目整体目标为锚点——README、架构文档（如 `docs/`）、specs 清单；确认库的实际用途与关键业务流，作为"架构与目标一致性"的判断基准；
     - 变更集模式：按以下优先级查找对应需求描述，找到后在报告中引用其路径/编号：
       1. 项目规格文档（如 `specs/<feature-id>/`、`docs/spec/`）；
       2. issue / PR 描述 / 任务管理工具编号；
       3. 用户在对话中给出的任务描述；
       4. 均未找到 → 将"需求对齐"类评价降级为待确认疑点，向作者索要任务描述，**禁止**凭代码自行臆测任务目标。
   - **调用方影响面（变更集/定点模式）**：变更涉及导出接口/schema/配置时，用引用搜索列出受影响的调用方，作为效率与可维护性评审的输入。

### 第二步：依赖安全审计（必需环节）

存在依赖清单时**必须**执行自动化审计并汇总结果，不允许只做静态清单核对：

| 生态 | 触发条件（存在任一清单文件） | 审计命令 |
|---|---|---|
| Node.js | `package.json` / `package-lock.json` / `pnpm-lock.yaml` / `yarn.lock` | `npm audit --json`（pnpm 项目用 `pnpm audit --json`，yarn 项目用 `yarn audit --json`） |
| Python | `requirements*.txt` / `pyproject.toml` + lock | `pip-audit -r requirements.txt`（无 pip-audit 时提示安装；Poetry 项目用 `poetry show --outdated` 辅助） |
| Go | `go.mod` | `govulncheck ./...`（未安装时报告并注明未执行原因） |
| Rust | `Cargo.toml` / `Cargo.lock` | `cargo audit` |
| .NET | `*.csproj` | `dotnet list package --vulnerable` |

执行要求：

1. 审计命令在项目根目录运行；命令执行失败或工具未安装时，在报告中注明"未执行原因"，不得静默跳过。
2. 结果汇总进报告的**"安全审计结果"**小节：漏洞数量按严重级别统计，高危/严重漏洞逐条列出包名、版本、CVE 编号、修复版本建议。
3. 审计发现的可利用漏洞（与变更代码中的调用点相关）按 P0/P1 计入问题清单；仅为传递依赖、无调用点的漏洞记入审计小节并建议升级。
4. 检查 lockfile 是否提交、版本是否被通配符（`*`、`latest`）放宽锁定。
5. 项目无任何依赖清单（如纯脚本）时，跳过本步并在报告中注明。

### 第三步：执行评审（静态检查 → 逻辑 → 安全 → 性能 → 可维护性 → 架构）

工具先行、人工跟进，前序阶段的输出是后续分析的输入。

**阶段 A：静态检查（必须先于人工分析执行）**

项目存在对应工具链时依次运行并汇总结果；工具未配置/未安装时在报告注明并跳过，**不得虚构工具结果**：

- lint / 格式检查：`eslint` / `ruff` / `golangci-lint` / `cargo clippy` 等（以项目实际配置为准）；
- 类型检查：`tsc --noEmit` / `mypy` / `pyright` 等；
- 编译 / 构建：确认可构建、无阻断错误；
- 既有测试套件：运行并区分"既有失败"与"本次新增失败"——后者是逻辑分析的重点线索。

工具告警**不直接进问题清单**：与本次变更相关且需人工判断的，转化为对应维度问题（注明"由 <tool> 发现"）；纯风格类留给工具与项目格式化配置，不重复报告。

**阶段 B-F：人工分析（按顺序逐层推进）**

| 阶段 | 分析动作 | 使用清单 |
|---|---|---|
| B 逻辑分析 | 控制流、边界条件、错误处理路径、并发竞态；结合测试结果定位可疑路径 | 语言专项清单（如有）+ 通用清单 |
| C 安全漏洞 | 依赖审计结果 + 注入、越权、敏感信息泄露核查 | `references/security-checklist.md` |
| D 性能 | 算法复杂度、N+1、资源泄漏、可扩展性核查 | `references/performance-checklist.md` |
| E 可维护性 | 可读性、复用、测试覆盖、文档完整性核查 | `references/maintainability-checklist.md` |
| F 架构对齐 | 对照需求来源评估结构、模块划分、依赖方向，识别过度设计/设计不足 | `references/architecture-checklist.md` |

**全库模式执行编排（主线路径，覆盖整个代码库）**

大库不可能逐文件通读，采用「跨切面扫描保覆盖 + 重点深审保深度 + 抽样兜底」三层编排：

1. **跨切面全库扫描（覆盖 100% 文件，grep/索引驱动，不逐文件通读）**：
   - 安全类：硬编码密钥/凭证模式、SQL 字符串拼接、`eval`/危险 API、命令注入风险点；
   - 效率类：循环内查询/请求、`SELECT *`、无界查询、未复用连接；
   - 一致性类：重复代码块（>=10 行相似片段）、未引用的死代码/导出、配置硬编码与环境变量漂移、TODO/FIXME 密度；
   - 结构类：验证第一步摸底发现的疑似循环依赖与跨层引用（逐个取证确认或排除）。
2. **重点模块深审（Top-N 模块，逐文件走阶段 B-F）**：每个模块深审完即输出该模块小结（问题 + 模块健康度），再进入下一模块——支持中断续跑，不依赖单次会话跑完全库。
3. **外围模块抽样（兜底）**：未进 Top-N 的模块按比例抽查（默认抽 20% 或至少 2 个文件），抽样依据 = 静态检查告警密度 + 文件规模 + 最后修改时间；抽样发现高密度问题时升级该模块为深审对象。
4. **上下文预算纪律**：优先使用聚合工具（LSP 索引、grep 聚合统计、依赖图）定位，再精读命中文件；单模块深审时只加载该模块文件，避免跨模块无谓读入。

**变更集/定点模式**：跳过上述编排，阶段 B-F 直接作用于指定范围；但「跨切面全库扫描」中与变更调用点相关的模式（如注入点上游校验缺失）仍需顺带核查。

执行要求：

- 按清单逐项核对，但**不要机械罗列**——只报告在评审范围中实际发现的问题。
- 每个发现的问题必须定位到具体文件与行号（或函数/组件名），引用最小必要代码片段。
- 区分"确认的问题"与"待确认的疑点"：无法从代码本身确证的问题（如缺少业务上下文）标注为疑点，说明需要向作者确认什么。
- **跨文件、跨模块的系统性问题（分层混乱、循环依赖、重复实现、所有权不清）在库级报告中优先于局部问题**——全库回顾的核心价值正是发现单模块视角看不到的系统性问题。
- **问题必须验证**：报告的 bug（逻辑错误、崩溃、数据损坏）应尽量运行复现——执行相关测试、构造最小复现脚本或运行静态检查确认；无法运行时明确标注"未经运行验证"，不得将推测表述为事实。
- **覆盖度声明**：全库报告必须写明——跨切面扫描覆盖率（100% 文件）、深审模块清单、抽样比例与抽样对象，未覆盖部分明确声明，不得暗示已全量深审。

### 第四步：评定严重程度

每个问题按以下四级评定：

| 级别 | 含义 | 判定标准 |
|---|---|---|
| **P0 阻断** | 必须修复后才能合入 | 安全漏洞（注入、密钥泄露、越权）、数据损坏风险、核心功能错误 |
| **P1 严重** | 应尽快修复，可短期带病运行 | 性能瓶颈导致明显劣化、破坏分层/模块边界的架构问题、缺失关键错误处理 |
| **P2 建议** | 应当修复但不阻塞 | 可维护性问题、重复代码、测试缺口、文档缺失 |
| **P3 提示** | 可选优化 | 风格建议、更优替代方案、前瞻性改进 |

评定原则：以"造成的实际风险"为准，而非"违反了多少条规则"；同一根因的多个表象合并为一条问题。

**三档沟通口径映射**（对外沟通、统计汇总时使用；问题条目仍保留 P 级精度）：

| 三档口径 | 包含 | 含义 |
|---|---|---|
| 严重 | P0 + P1 | 阻塞合入或需尽快修复 |
| 一般 | P2 | 应当修复但不阻塞 |
| 建议 | P3 | 可选优化 |

定级阈值不是常量：第七步的自迭代会依据分级偏差数据修订本节判定标准。

### 第五步：输出结构化评审报告

按 `references/report-template.md` 的格式输出报告，要求：

1. **总体评价**（2-4 句）：变更集模式 → 代码是否达到可合入标准；全库模式 → 库级健康度结论（架构、安全、效率、可维护性四维评分）与最大风险。
2. **问题清单**：按严重程度 P0 → P3 排序，每条包含：
   - 问题分类（架构 / 安全 / 效率 / 可维护性）；
   - 严重程度（P0-P3）；
   - 具体位置（文件路径 + 行号或符号名）；
   - 问题描述（现状 vs 期望，引用最小代码片段）；
   - 改进建议（具体、可操作的修改方式，必要时给出示例代码）。
3. **全库模式附加章节**（变更集模式无此章节）：
   - **模块覆盖与热度表**：每个模块的评审深度（深审/抽样/仅扫描）、问题数、健康度简评；
   - **跨模块系统性问题**：单列报告（合并同类模块的共性问题的代表性样例 + 影响面清单）；
   - **整改路线**：按「先 P0 安全 → 再 P1 架构/性能 → 后 P2/P3」排列的批次化建议，每批标注预估范围与依赖顺序。
4. **待确认疑点**：需要作者/用户补充上下文的问题。
5. **亮点**（可选）：值得肯定的设计或实现，帮助校准评审基调。

### 报告语言

- 报告正文使用用户对话语言（默认简体中文）；
- 代码、标识符、文件路径、技术术语保持英文原样；
- 用户在项目规范中另有语言约定时，遵循项目约定。

### 第六步：验证与闭环

报告输出后不终止流程，执行以下闭环动作：

1. **修复询问**：
   - 变更集模式：主动询问是否修复 P0/P1 问题；同意后按严重程度从高到低逐项修复，每修复一项即运行对应验证（测试/复现脚本/审计命令），确认问题消除；P3/P2 仅在用户明确要求时处理。
   - 全库模式：P0/P1 通常成规模，不默认逐项修复——先与用户确认**整改批次**（按第五步整改路线），再逐批修复；每批完成后复验并更新模块健康度，用户可随时暂停。
2. **复审**：修复完成后必须复审——重新获取 diff（仅限修复改动），核对：
   - 原报告的 P0/P1 问题是否确实消除（逐条标注"已修复/未修复"）；
   - 修复本身是否引入新问题（新改动同样走四维评审与依赖审计，但只针对增量）。
3. **回归核对**：项目存在测试套件时，修复后运行相关测试，确认无回归；测试失败则继续修复或如实报告。
4. **闭环终止条件**：P0/P1 全部消除且无新增问题 → 报告"评审通过"；用户明确表示暂不修复 → 在报告中保留未修复问题清单后终止（全库模式保留整改路线供后续批次使用）。

### 第七步：自迭代与经验沉淀

每次评审收尾时**自动执行**复盘（不需用户触发），目标是让下一次评审更准、更全。

1. **收集复盘数据**：
   - **问题类型分布**：本轮问题按「维度 × 语言/框架 × 问题模式」归类统计；
   - **误报**：被作者/用户反驳成立、或复审证明不成立的问题，记录原因（清单规则过宽 / 上下文不足 / 工具误报）；
   - **遗漏**：评审时未发现、后续（修复期 / 复审 / 用户反馈）才暴露的问题，记录原因（清单缺该模式 / 检查顺序不当 / 被工具告警淹没）；
   - **分级偏差**：定级过高或过低的问题（如风格问题定 P1、数据损坏风险定 P2）及原因。
2. **生成改进建议**（按四类输出）：
   - **调整检查规则**：收窄高误报规则的触发条件，或为漏检模式补强规则表述；
   - **补充问题模式**：将本轮验证过的新模式写入对应 `<dimension>-checklist.md`，或沉淀为新的 `<language>-checklist.md`（遵循语言专项扩展点的确认规则）；
   - **优化分级阈值**：依据分级偏差修订第四步的判定标准与示例；
   - **更新输出模板**：报告结构若有信息缺失（用户反复追问的点），修订 `report-template.md`。
3. **落地方式**：
   - 每轮复盘**追加**一条记录到 `references/iteration-log.md`（格式见该文件）；高频误报/遗漏同步滚动进该文件的"高频"段；
   - 涉及清单、模板、定级标准的修改，先向用户展示改动点，**经确认后**写入对应文件；单轮只改本轮数据支持的部分，不趁机重构无关内容；
   - 用户要求全自动落地时，可在报告中标注"已自动更新"并直接写入，但每轮自动改动不超过 3 处，超出部分仍需确认。
4. **下次评审的运用**：第一步开始时读取 `references/iteration-log.md` 的最近 3 条记录与"高频误报/遗漏"段，作为本轮评审的校准输入（优先核查历史遗漏模式、放低历史误报模式的出现阈值）。

## 语言专项扩展点

`references/` 目录预留语言/框架专项清单的扩展位，用于逐步沉淀各栈深水区知识：

### 命名规范

- 文件名：`<language>-checklist.md`，language 使用小写惯用名：`react`、`vue`、`typescript`、`python`、`go`、`rust`、`java`、`fastapi`、`django`、`nestjs`、`docker`、`terraform` 等；
- 框架专属清单独立成文件（如 `react-checklist.md`），不合并进语言文件。

### 文件内容约定

每个语言专项清单遵循统一结构，与四维框架对齐：

```markdown
# <语言/框架> 专项评审清单
## 专属陷阱          # 该栈易犯、通用清单覆盖不到的深水区问题
## 惯用法与反模式    # 社区公认的最佳实践与已知反模式
## 安全专项          # 该栈特有安全风险（补充 security-checklist.md）
## 性能专项          # 该栈特有性能坑（补充 performance-checklist.md）
## 工具链检查        # 该栈专属 lint/test 工具及应交给工具的问题
```

### 加载规则

1. 第一步识别项目类型后，检查 `references/` 下是否存在匹配的 `<language>-checklist.md`：存在 → 在第三步**与四份通用清单一并加载**；不存在 → 仅用通用清单，不做降级提示。
2. 一个项目命中多个清单（如全栈项目 `react` + `fastapi`）时全部加载。
3. 评审中发现值得沉淀的栈专属问题、且通用清单未覆盖时，在报告末尾提示用户"可将此模式沉淀为 `<language>-checklist.md`"，经用户确认后再创建文件。

## 约束

- 只读评审：除报告文件外不修改任何代码，除非用户明确要求直接修复。
- 不臆测需求：设计层面的评价须基于可观察到的代码结构与文档，避免"我认为应该……"式的主观偏好。
- 报告默认直接输出到对话；仅当用户要求保存为文件时才写入文件（位置遵循项目文件放置规范）。
- 评审结论必须可复现：每条问题附文件与行号，便于作者直接跳转。
